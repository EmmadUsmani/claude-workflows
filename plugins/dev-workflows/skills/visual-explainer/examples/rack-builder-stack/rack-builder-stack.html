    The first use is the outermost layer.

    Rack::Builder reads config.ru without calling anything. It records one closure per use, then folds them from last to first around your app. This page traces that fold, the one place where it is not top-to-bottom (map), and what a request does on the way in and out.

    Code read atmain @ da90464 StateBehaviour of rack main today · no fix involved EvidenceRuby probe · 6 cases reproduced
    The answer
    • use M stores proc { |app| M.new(app, ...) }. Nothing is built yet. builder.rb:164
    • to_app runs @use.reverse.inject(app). The last use wraps the app first, so the first use ends up outermost and sees the request first. builder.rb:271
    • A use written after a map only wraps the default app. It never runs for the mapped paths. builder.rb:160-163, reproduced in probe case 2.
    • Middleware that must act after the body is sent wraps the body in Rack::BodyProxy, whose block runs when the server calls close. body_proxy.rb:28-36

    1Reading config.ru only records closures

    The file is eval'd with the builder as self lib/rack/builder.rb:65-111

    • parse_file sends a .ru path to load_file. Any other path is required, and the constant named after the file is returned (app.rb → App). :65-72
    • load_file strips a UTF-8 BOM, raises on an old #\ -p 9292 option line, and drops everything after __END__. :87-98
    • new_from_string evaluates the text in BUILDER_TOPLEVEL_BINDING.call(builder), then returns builder.to_app. :102-111
    • Why a binding and not instance_eval(String): the source comment says instance_eval "would resolve constants differently". :105-106

    2to_app folds the closures from last to first

    # lib/rack/builder.rb:267-274
def to_app
  app = @map ? generate_map(@run, @map) : @run
  fail "missing run or map statement" unless app
  app.freeze if @freeze_app
  app = @use.reverse.inject(app) { |a, e| e[a].tap { |x| x.freeze if @freeze_app } }
  @warmup.call(app) if @warmup
  app
end

    Builder#call rebuilds the stack on every request lib/rack/builder.rb:279-281

    call(env) is to_app.call(env). Every call makes new middleware instances and runs warmup again. Probe case 4 called a builder 3 times and warmup ran 3 times. A server should call to_app once and keep the result.

    3A use after a map never sees the mapped paths

    This is the one place where file order is not stack order. Pick a config.ru and a path. The simulator applies the same rules as builder.rb and urlmap.rb. Its outputs match the probe.

    Why: a pending map is pushed onto @use as one more closure lib/rack/builder.rb:159-167, 287-291
    
    
    # lib/rack/builder.rb:159-164
def use(middleware, ...)
  if @map
    mapping, @map = @map, nil
    @use << proc { |app| generate_map(app, mapping) }   # app = everything declared below
  end
  @use << proc { |app| middleware.new(app, ...) }
    
    
      
      
    • In the fold, closures written later run first. So by the time the map closure runs, app is the endpoint already wrapped by every later use.
      • 
      
    • generate_map puts that wrapped app at '/', and builds each map block as a fresh Builder seeded with it. :288-289
      • 
      
    • A map block that has its own run replaces that default. That is why /api skips the later middleware.
      • 
      
    • A map block with no run inherits the wrapped default (spec "accepts middleware-only map blocks", spec_builder.rb:201).
      • 
    
    
    
    What to do. Put middleware every path needs above the first map, or repeat the use inside each map block. No spec in the repo asserts the "after map" case. The evidence is probe case 2.
    
  
    

  
    
    
    4URLMap tries the longest prefix and moves it into SCRIPT_NAME
    
    
      
      
    • remap sorts entries with a host first, then by path length, longest first. urlmap.rb:43-45
      • 
      
    • Each path compiles to \A<path>(.*). The rest must be empty or start with /, so /a does not match /ab. :40, :71
      • 
      
    • On a match: SCRIPT_NAME += location, PATH_INFO = rest, then app.call(env). :73-76
      • 
      
    • No match returns 404 with x-cascade: pass. :79
      • 
      
    • An ensure puts both keys back as soon as app.call returns, before the body is read. :81-83

    5On the way out, BodyProxy defers work until the server closes the body
    
    
    A middleware returns from call before the client has the body. Anything that must happen after the body is sent (unlocking, logging) goes in a BodyProxy block.

    What to do with this
    
    
      
      
    • Order: write use lines outermost first. The first one sees the raw request and the final response.
      • 
      
    • Maps: put shared middleware above every map. A use below a map silently skips the mapped paths.
      • 
      
    • Servers: call to_app once. Builder#call rebuilds the stack on every request.
      • 
      
    • Lint: Builder never adds Rack::Lint. Opt in for tests with Rack::MockRequest.new(app, lint: true).
      • 
      
    • After-response work: wrap the body in Rack::BodyProxy. Don't do it at the end of call.
