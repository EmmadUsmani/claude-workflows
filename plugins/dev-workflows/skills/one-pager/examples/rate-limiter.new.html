04

HTTP contract

headers · 429
# allowed HTTP/1.1 200 OK RateLimit-Limit: 60 RateLimit-Remaining: 41 RateLimit-Reset: 19 # s until full # bucket empty HTTP/1.1 429 Too Many Requests Retry-After: 2 # s until 1 token {"error":"rate_limited","retry_after":2}
  • Unchanged: every other status, header and body. Config: enabled, store, exempt.
  • Why these header names · D7: they follow the IETF RateLimit draft, which clients and proxies already parse. X-RateLimit-* was rejected: every API spells it differently.
05

Consumer · token bucket

app + bundled client
# config.ru use Pocketweb::RateLimit::Middleware, store: RedisStore.new(REDIS), exempt: ["/health"] # Pocketweb::Client: honour 429 if res.code == "429" && tries < 3 sleep res["Retry-After"].to_f retry end
  • Why a token bucket · D1: a fixed window lets twice the limit through across a window edge. The bucket allows one burst of capacity, then a steady refill_per_sec.

Guarantees · open items

rollout: 3 PRs
  • Off by default: enabled: false uses NullStore, so responses are byte-identical to today.
  • No key gets more than capacity requests in a burst, across all processes (D4).
  • O1 a lower tier for anonymous ip: keys? Proposed: anonymous 20 / 0.2.
  • Fail open on a store error or timeout: the request is allowed and counted (D6).
  • Why three PRs: each ships alone. L1 has no reader, L2 is off by default, L3 acts only when enabled flips.
  • Out of scope: per-route costs, quotas shared across regions.
