Render Cache Key Collision — RCA

Verdict: the cache key is the source text only, so HTML rendered with safe: false is served to a safe: true caller that renders the same text.

How it got in

history · repro
H · history (git log, PR bodies)
H12.3.0 · #118 adds RenderCache, key = SHA256(src)
options were global then (Inkdown.configure): correct when written
H22.4.0 · #131 adds per-call render(src, safe:)
cache_key untouched; options now vary per call
H3cache on by default since 2.3
every 2.4.x app that mixes modes is exposed
R · reproduction, one process
R1render(src, safe: false) → miss, write
R2render(src, safe: true) → HIT → raw HTML
R3Inkdown.cache.clear; repeat R2 → escaped
proves the cache, not the renderer, is at fault
Ruled out
  • The sanitizer: with the cache off, safe: true escapes every case in the report.
  • Thread races: the repro is single-threaded and deterministic.
WHY THE TESTS MISSED IT

Every spec clears the cache first (before { Inkdown.cache.clear }) and renders with one option set. No spec renders one text with two option sets, so no spec could see a second caller.

04

The fix

PR #142 · on branch, not released
# lib/inkdown/render_cache.rb (fix/cache-key-options) def cache_key(src, options) Digest::SHA256.hexdigest([ Inkdown::VERSION, options.cache_fingerprint, # every attr, sorted src ].join("\0")) end
  • Why every option, not just safe · D1: hard_wrap and autolink change output too. Listing one option would leave the next one to repeat the bug.
  • Why the version: an upgrade that changes rendering would otherwise keep serving the old HTML.

SEVERITY: HIGH · stored XSS

Untrusted text can run script in readers’ browsers. Why not critical: the attacker needs a trusted caller to render the identical text first, in the same process.

06

Remediation · follow-ups

rollout strip
  • Users: upgrade to 2.4.4. Until then, Inkdown.cache = nil or one cache per mode.
  • No flush needed: new keys never match old entries, which age out of the LRU.
  • Follow-up: a spec that flips each Options attribute and expects a new key. Why: it catches the next option nobody remembers.
